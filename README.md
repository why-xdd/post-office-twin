# Цифровой двойник отделения Почты России

Веб-сервис для работы с цифровым планом отделения: 2D-редактор плана, справочники зон и
оборудования, инвентаризация, проверка корректности планировки по отраслевым нормам и упрощённое
3D-представление.

**Работающий сервис:** https://plan-ops.onrender.com — вход без регистрации и пароля. Первое открытие после
простоя может занять до минуты: бесплатный хостинг усыпляет службу.

Чтобы пройти основной сценарий: «Открыть пример» → на плане отмечены нарушения → «Исправить
автоматически» → «Применить» → «Сохранить версию» → вернуться к списку планов и открыть план снова.

## Технологии

React, TypeScript, Vite, three.js на клиенте. Python 3.12, FastAPI, shapely, networkx на сервере;
планы хранятся в SQLite или PostgreSQL. Запуск — Docker Compose, развёртывание — Render. Все
зависимости под лицензиями MIT, BSD или Apache-2.0.

## Запуск

```bash
docker compose up -d --build
```

Сервис откроется на http://localhost:8000: сайт, API и документация API (`/docs`) — с одного
адреса. Планы хранятся в томе `plan-data` и переживают перезапуск контейнера.

Без Docker, для разработки:

```bash
cd services/api && uv sync && uv run uvicorn app.main:app --reload   # API на :8000
cd apps/web && npm install && npm run dev                           # клиент на :5173
```

Если клиент собран (`npm run build`), API отдаёт его сам, и отдельный сервер для клиента не
нужен.

Хранилище выбирается переменной `DATABASE_URL`: если она задана, планы лежат в PostgreSQL, иначе —
в файле SQLite (`OPS_TWIN_DB`, по умолчанию `storage/plans.sqlite`). Все переменные — в
`.env.example`.

### Развёртывание

`render.yaml` описывает развёртывание на Render: веб-служба из корневого `Dockerfile` и база
PostgreSQL. В панели Render: New → Blueprint → репозиторий. `/health` используется как проверка
готовности.

## Данные

Формат плана — формат заказчика (`data/example_plan.json`), расширенный необязательными полями:
координаты в метрах, начало отсчёта — левый нижний угол, `position` у оборудования означает центр
объекта, `size_m` — габариты по осям X и Y. Файл заказчика открывается без конвертации, а поля,
которых сервис не знает, сохраняются при записи как есть.

Собственные поля плана:

| Поле | Где | Зачем |
|---|---|---|
| `dictionaries` | план | Свои типы оборудования и зон: справочник расширяется без изменения кода |
| `attributes` | объект | Атрибуты по схеме типа: номер окна, число ячеек, IP-адрес |
| `inventory` | объект | Учётные данные: инвентарный номер, поставщик, модель, даты осмотров |
| `staff`, `integrations` | объект | Закреплённый сотрудник и связи с учётными системами |
| `height_m` | объект | Своя высота вместо справочной — для объёмного вида |

### Демонстрационное отделение

`data/demo_plan.json` — отделение «Заречное», придуманное и нарисованное в редакторе: Г-образный зал
126,25 м², шесть зон (операционный зал, тамбур, зона ожидания, накопитель очереди, служебная зона,
комната персонала), 33 объекта с инвентарными данными и свой тип оборудования «Стол сортировки
РПО», которого нет во встроенном справочнике. Кнопка «Открыть пример» открывает именно его.

В плане оставлены проблемы, на которых видна работа проверок и ассистента: терминал очереди и
скамья зажимают проход от входа до 0,74 м, сейф заходит на стеллаж, стеллаж возвратов стоит в
клиентском зале, хотя по справочнику ему место в служебной зоне, не хватает почтового ящика по
перечню оборудования. Ассистент снимает все три ошибки за две перестановки.

Планы отделений синтетические. Реальные планы БТИ не используются.

## Ассистент планировки

Ассистент подбирает расстановку и объясняет каждое предложение: что изменить, почему (со ссылкой
на пункт норматива) и какой будет эффект. Решение принимает человек — рекомендация сначала
показывается на плане и применяется только по кнопке.

Варианты сравниваются по одной величине, в которую входят нарушения норм, ширина прохода для
маломобильных посетителей, проходимость подхода к каждому окну, число мест ожидания, средний путь
посетителя и суммарная величина переноса оборудования (`app/assistant/objective.py`). Так
устранение нарушения не достигается ценой удобства: например, скамья не уезжает из зоны ожидания
просто потому, что «так меньше ошибок».

### Обучаемый ускоритель поиска

Полная проверка одного варианта расстановки стоит дорого: для нового объекта сервис порождает
сотни мест, а полный перебор всех занимает в среднем 13 секунд. Поэтому полностью проверяется
только верхушка списка — 24 места, — а порядок этой верхушки задаёт модель: градиентный бустинг
на решающих деревьях, обученный на данных, которые сервис порождает сам. Для каждой позиции
известно, чем закончилась полная проверка и какой получилась расстановка целиком.

Голов две, и они отвечают на разные вопросы:

- **первая — «пройдёт ли место полную проверку»**: отсеивает места, добавляющие нарушения;
- **вторая — «войдёт ли место в лучшие 5 % допустимых мест своего списка»**: поднимает наверх
  самые удачные для расстановки в целом — по ширине прохода, пути посетителя, местам ожидания.

Признаков 42: геометрия места относительно стен, проёмов и зон, запас по проходу и, отдельно,
положение относительно потока посетителей — расстояние до линий от входа к окнам и к типичным
маршрутам плана, пересечение с ними, насколько место сужает путь.

Главная мера — сквозная: тот же подбор места, что в сервисе (`search.place`), на 24 свежих
синтетических планах, которых модель не видела, и двух настоящих — 180 задач «поставить объект»
(`scripts/benchmark_placement.py`). Эталон — полный перебор всех мест.

| Порядок проверки | Проверяется мест | Проигрыш перебору | Нашёл лучшее место | Не нашёл ни одного | Время |
|---|---|---|---|---|---|
| Без модели | 24 | 1,33 | 62 % | 6 | 1,24 с |
| Одна голова | 24 | 1,00 | 67 % | 4 | 1,27 с |
| **Две головы** | 24 | **0,12** | **92 %** | **3** | 1,28 с |
| Без модели | 12 | 1,95 | 59 % | 7 | 1,08 с |
| **Две головы** | 12 | **0,28** | **86 %** | **6** | 1,13 с |

Проигрыш — насколько выбранное место хуже лучшего из всех в единицах цели (меньше — лучше).
С моделью подбор почти не уступает полному перебору и идёт в 10 раз быстрее него.

Метрики на отложенных помещениях (обучение делится по планам, а не по строкам):

| Показатель | Значение |
|---|---|
| Размеченных позиций | 240 498 |
| Площадь под ROC первой головы | 0,975 |
| Доля верных ответов первой головы | 0,947 |
| Подходящих мест в первых 10 — с моделью / без | 0,93 / 0,77 |
| Лучшее место в первых 24 — две головы / одна / без модели | 0,94 / 0,77 / 0,73 |
| Лучшее место в первых 10 — две головы / одна / без модели | 0,90 / 0,71 / 0,71 |

Вторая голова пробовалась в нескольких видах. Лучшее место попадало в первые 10 при регрессии на
величину цели в 73–79 % списков, при LambdaRank по уровням качества — в 87 %, при классификации
«лучшие 5 %» — в 90 %. LambdaRank к тому же после 5–10 деревьев начинает портить верхушку: он
выравнивает весь список, где большинство пар — «среднее против плохого». Классификация обучается
устойчиво; LambdaRank остаётся доступен ключом `--quality-target lambdarank`.

Вторая голова включается только для нового объекта. При перестановке уже стоящего объекта
(автоисправление) порядок задаёт первая голова: на 32 синтетических планах с нарушениями вторая
голова там мешала — оставалось 5–6 ошибок против 3. На учебном плане заказчика автоисправление с
моделью снимает все нарушения за 17 секунд, без модели остаётся одно нарушение за 31 секунду
(`scripts/benchmark_assistant.py`).

Сервис не зависит ни от одной библиотеки машинного обучения: деревья лежат в
`app/assistant/accelerator_model.json`, обход написан в `app/assistant/accelerator.py`, обучение —
в `scripts/` и в поставку не входит. Без файла модели сервис работает так же, только подбирает
менее прицельно.

Переобучить и замерить эффект:

```bash
cd services/api
uv run python scripts/train_accelerator.py --plans ../../data/example_plan.json ../../data/demo_plan.json --synthetic 180 --per-type 200
uv run python scripts/benchmark_placement.py --synthetic 24
uv run python scripts/benchmark_assistant.py --plans ../../data/example_plan.json
```

Обучающие планы синтетические: генератор делает и прямоугольные залы, и Г-образные, с разной
глубиной, входом с разных сторон и разной загруженностью оборудованием. Реальные планы БТИ не
используются.

### Команды и вопросы словами

Поле «Скажите, что сделать» понимает фразы вида «поставь две кассы у перегородки», «убери
банкомат», «перенеси скамью в зону ожидания», «сделай проход шире». Фразу разбирает сам сервис
(`app/assistant/language.py`), а места и последствия считает тот же расчёт, что и в панели
ассистента. Если часть фразы не разобралась, сервис так и говорит, а не додумывает.

Вопрос отличается от команды и ничего в плане не меняет — на него сервис отвечает:

| Фраза | Ответ |
|---|---|
| сколько окон обслуживания? | Окно обслуживания: 3 — Окно №1, Окно №2, Окно №3. |
| сколько скамеек в зоне ожидания? | Скамья в зоне «Зона ожидания»: 2 — Скамья ожидания 1, Скамья ожидания 2. |
| где стоит банкомат? | Банкомат (О-10) — зона «Операционный зал», 7.9 × 0.4 м. |
| какая свободная площадь? | Площадь 126,25 м², занято 17,45 м², свободно 108,8 м². |

Разбор терпим к тому, как люди пишут: числа из адреса объекта не считаются количеством
(«поставь почтовый ящик О-12» — один ящик), слова с опечатками узнаются по близости написания
(«паставь термнал очереди»), а слова зон не путаются с названиями предметов («скамейку в зону
ожидания»). Мера разбора — батарея фраз в `tests/test_language.py`: 31 команда и вопрос, которые
сервис обязан понять, и 10 фраз, которые обязан не понять, а переспросить.

Заключение по плану — готовый текст для согласования: что проверено, что нарушено, что
предлагается и каким будет эффект. Собирается из посчитанных чисел, поэтому для одного и того же
плана всегда одинаково.

## Учёт в 1С

Во вкладке «Инвентарь» план выгружается описью для учётной системы и сверяется с ней обратно.

- **Опись для 1С** — таблица CSV (UTF-8, разделитель «;»): инвентарный номер, наименование,
  серийный номер, изготовитель, модель, местонахождение, идентификатор на плане, даты осмотров.
  В 1С загружается через загрузку из табличного документа.
- **Сверка с ведомостью** — ведомость основных средств из 1С, сохранённая в CSV, против
  оборудования на плане. Сервис показывает, что числится, но на плане его нет, что стоит на плане,
  но не числится, что стоит не в той зоне, где числится, и у чего расходится серийный номер.
  Строки сопоставляются по инвентарному номеру, затем по серийному; написание номеров
  («ЗР-000001», «зр 000001») не важно. Заголовки колонок узнаются по смыслу, шапка отчёта над
  таблицей пропускается, кодировка — UTF-8 или Windows-1251.

Попробовать: открыть пример, «Эксплуатация» → «Инвентарь» → «Сверить с ведомостью» →
`data/1c_inventory_sample.csv`. В этой синтетической ведомости заложено по одному расхождению
каждого вида, сервис находит все четыре. API: `POST /api/exchange/1c/export`,
`POST /api/exchange/1c/reconcile`.

## Очередь по данным отделения

Расчёт пропускной способности в панели ассистента опирается на среднесуточный поток из плана и
допущение о часе пик. Если у отделения есть данные, то же самое считается по часам из них:

- **журнал электронной очереди** (талон: выдан, вызван, завершён, окно, услуга) даёт поток,
  фактическое ожидание и фактическое время обслуживания;
- **почасовой счётчик посетителей** на входе (в том числе камера с подсчётом людей) даёт только
  поток; к окнам и к выдаче посылок он делится по долям маршрутов плана.

Для каждого часа сервис сравнивает фактическое ожидание с моделью M/M/c при окнах с плана и
считает, сколько окон нужно, чтобы среднее ожидание не превышало 5 минут. Отсюда выводы: в какие
часы окон не хватает, сколько окно-часов в день реально нужно по сравнению с открытыми, совпадают
ли часы пик по данным с указанными в плане.

Попробовать: панель «Ассистент» → «Загрузить журнал очереди» → `data/queue_log_sample.csv`. Это
синтетический журнал за 5 дней: поток и часы пик взяты из плана, обслуживание смоделировано
(`scripts/make_queue_sample.py`). На нём видно, что трёх окон обслуживания хватает с запасом
(открыто 36 окно-часов в день, достаточно 18), а единственной стойке выдачи в вечерний пик нужна
вторая. API: `POST /api/capacity/log`.

## Камера зала

Камера в отделении обычно уже висит. Вкладка «Камера» в режиме «Эксплуатация» превращает её запись
в цифры по плану: сколько посетителей в зале, где они стоят и хватает ли им места.

Как это устроено, по шагам — каждый можно объяснить проверяющему:

1. Запись раскладывается на кадры **прямо в браузере**, один кадр в секунду. На сервер уходят
   только уменьшенные кадры, поэтому работает и на бесплатном хостинге, и с длинной записью.
2. Фон зала — 75-й перцентиль яркости каждого пикселя: стены и мебель стоят на месте и уходят в
   фон, а посетитель закрывает своё место лишь часть записи и остаётся виден. Медиана для этого не
   годится: очередь стоит подолгу.
3. Всё, что отличается от фона, чистится от ряби и разбивается на связные пятна.
4. Один раз отмечаются четыре угла пола на кадре и то, чему они соответствуют на плане. По ним
   строится гомография, и точка опоры каждого пятна переводится в метры плана.
5. Точка попадает в зону плана, и получается: сколько человек в зоне ожидания, в накопителе
   очереди и у окон, в каждую секунду записи. Плюс тепловая карта — слой прямо на чертеже.

Нейросетей нет: обычное компьютерное зрение на numpy, ничего не грузится и не отправляется наружу.

**Точность.** Проверяется на синтетической записи, где известно, сколько людей в зале в каждую
секунду (`scripts/make_camera_sample.py` — посетители ходят по маршрутам демо-плана, вид сверху).
На 90 секундах записи: в среднем 10,4 человека по симуляции против 10,4 по видео, в пике 19 против
20, среднее расхождение 5 %. В накопителе очереди — в пределах одного человека. Проверка
повторяется тестом `tests/test_vision.py::test_matches_the_simulation_on_the_demo_recording`.

**Чего метод не умеет:** различать людей в плотной толпе. Слипшиеся силуэты считаются по площади
пятна, поэтому пик — оценка снизу. Человек, простоявший всю запись без единого движения, уйдёт в
фон. Всё это сервис пишет в допущениях рядом с результатом, а не прячет.

Попробовать: открыть пример, «Эксплуатация» → «Камера» → «Выбрать запись» → `data/camera_sample.mp4`,
отметить четыре угла пола (в демо-записи это углы кадра) → «Разобрать запись».
API: `POST /api/vision/analyze`.

## Объёмный вид

Кнопка «Объём» показывает тот же план в трёх измерениях: стены с проёмами и перемычками над
дверями, оборудование в его настоящих габаритах, типовые маршруты посетителей лентами по полу и
две фигуры у входа для чувства масштаба — человек ростом 1,7 м и кресло-коляска шириной 0,9 м.
Объекты, участвующие в нарушениях, окрашены и помечены меткой сверху: цвет не единственный признак.

Высоты не выдуманы: они лежат в справочнике типов (`height_m` и `mount_height_m`, высота низа над
полом для настенного оборудования) и редактируются вместе с планом, а у конкретного объекта может
быть своя высота. Поэтому объём соответствует плану, а не представлениям о том, как выглядит
отделение.

Качества рисования два, переключаются кнопкой и запоминаются:

- **Покрасивее** — физические материалы, мягкие тени, отражения помещения, сглаживание.
- **Попроще** — плоская заливка без теней и отражений. Нужен для слабой машины и чужого
  проектора; сервис переходит на него сам, если браузер выдаёт меньше 22 кадров в секунду, и
  говорит об этом. Без поддержки WebGL объёмный вид сообщает об этом и не мешает работать с планом.

Ракурсы «Изометрия», «Сверху» и «От входа» ставят камеру одним нажатием, вид сверху совпадает с
чертежом. Камерой можно управлять и с клавиатуры: стрелки вращают, плюс и минус приближают. Библиотека трёхмерной графики грузится только
при открытии объёмного вида и не утяжеляет редактор плана.

## Импорт чертежа

Экран «Чертёж в цифровой план» принимает картинку или PDF: сервис находит стены, перегородки и
проёмы, а масштаб берёт из одного числа — действительной ширины помещения, которую называет
человек. Распознавание не использует внешних библиотек компьютерного зрения: тёмные пиксели
считаются по строкам и столбцам, длинные сплошные полосы становятся стенами, светлые промежутки
внутри них — дверями и окнами (`app/importer/drawing.py`).

Результат — черновик: он открывается в редакторе вместе со списком того, что стоит проверить.
На контрольном чертеже 14 × 9 м сервис восстанавливает 13,92 × 8,92 м, находит перегородку и два
проёма. Оборудование и зоны расставляются уже в редакторе.

Реальные планы БТИ по условиям задачи не используются: распознавание проверено на синтетических
чертежах и собственных рисунках.

## Проверено на объёме данных

Редактор проверялся на планах в 100, 300 и 500 объектов (зал до 50 × 50 м), в Chromium, окно
1440 × 900:

| Объектов | План на экране | Перетаскивание объекта, средний кадр | Полная проверка плана |
|---|---|---|---|
| 100 | 0,13 с | 16,7 мс | 0,3 с |
| 300 | 0,17 с | 17,1 мс | 1,3 с |
| 500 | 0,15 с | 17,5 мс | 2,7 с |

Время открытия — с прогретым кэшем браузера; при первом открытии план на 500 объектов появляется
за 1,4 с. Перетаскивание держит 60 кадров в секунду на всех трёх объёмах: проверка идёт в фоне
после паузы в правке и не задерживает отрисовку. Реальное отделение — это 20–60 объектов.

Расчёты на стороне сервера, на одном ядре, с холодного старта (без кэша):

| Отделение | Объектов | Полная проверка | Исправить нарушения | Все рекомендации |
|---|---|---|---|---|
| Демо-отделение 15 × 9 м | 33 | 0,19 с | 2,5 с | 5,7 с |
| Зал 25 × 15 м | 11 | 0,04 с | 1,6 с | 7,2 с |
| Зал 25 × 15 м | 31 | 0,20 с | 4,1 с | 16,1 с |
| Зал 25 × 15 м | 61 | 0,60 с | 37 с | 26 с |

Подбор рекомендаций ограничен по времени (`OPS_TWIN_ASSISTANT_BUDGET`, по умолчанию 25 секунд):
когда отведённое время кончается, сервис отдаёт найденное и помечает ответ неполным, а не держит
человека в ожидании. Ответ на один и тот же документ считается один раз и запоминается на 30
минут, поэтому повторное открытие плана мгновенное. Шаг сетки поиска подбирается под площадь
области: на отделении обычного размера он 25 см, на зале в 400 м² — крупнее, иначе время росло
бы как площадь.

## Известные ограничения

- Стены — отрезки, в том числе наклонные, но привязка объектов к стенам рассчитана на
  горизонтальные и вертикальные стены.
- Помещение одноэтажное: лестницы, пандусы и перепады уровней не моделируются, пандус задаётся
  только параметрами для проверки.
- Путь посетителя строится по свободной площади пола, без учёта людей в очереди.
- Ассистент переставляет существующее оборудование и подбирает места для нового, но не меняет
  стены и зоны.
- Импорт чертежа распознаёт стены и проёмы на чертежах в линиях; фотографии помещений и
  рукописные схемы не распознаются.
- Запись с камеры разбирается по кадрам раз в секунду: короткие события между кадрами не видны.
  Люди в плотной толпе считаются по площади пятна, а не поштучно.
- Бесплатный хостинг усыпляет службу после 15 минут без запросов; база PostgreSQL на нём
  бесплатна 30 дней.
